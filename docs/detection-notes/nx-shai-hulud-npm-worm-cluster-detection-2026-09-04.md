# Two Campaigns Sharing a Name: The Nx Campaign Cluster (Now Five Vectors) and the Generic "Shai-Hulud" Pair

Six rules, two genuinely different things. Part A is four rules that complete a real, well-documented campaign cluster this corpus tracks (a fifth vector, `s1ngularity_nx_npm_token_exfil`, was covered in an earlier note — five total). Part B is two rules that share the "Shai-Hulud" name with a real, independently-disclosed npm worm but whose OWN description and detection logic never actually encode that campaign's specifics — worth reading as a documented content gap, not another vector of anything.

## Part A: The Nx Campaign 4-Vector Cluster (COMPLETE)

Microsoft's May 2026 disclosures and Docker's own incident writeup describe FOUR independent-but-related supply-chain compromise vectors converging on developers using the Nx build-system ecosystem and AI coding tools. This corpus tracks all four as sibling rules that explicitly cross-reference each other; vector 2 (`s1ngularity_nx_npm_token_exfil`, the compromised Nx CLI installer) was detailed in this corpus's earlier npm-supply-chain-worm-cluster note. Here are vectors 1, 3, and 4:

**Vector 1 — Mini Shai-Hulud: compromised npm packages with forged provenance (Microsoft Threat Intelligence, 2026-05-21).** The `antv` npm package family was compromised; a Bun preinstall hook activates post-install and the attacker forges SLSA provenance attestations to make the malicious release look legitimately signed. Post-install egress reaches a C2 endpoint at the `m-kosche.com` domain family (canonical IOC `t.m-kosche.com`) or hardcoded IP `185.95.159.32`, for credential theft and further worm propagation. WRG's own defensive note in this rule's description: the NextDNS feed already blocks this domain at the network layer (a sister OPSEC infrastructure ship from 2026-05-19) — this Sigma rule adds a SIEM-side detection layer for log enrichment and retrospective hunting on top of that existing block, not a replacement for it.

**Vector 3 — nx-console VS Code extension: an ~11-minute malicious publish window with a novel provenance bypass (StepSecurity, 2026-05-18).** An orphan commit payload was published from the OFFICIAL `nrwl/nx` GitHub repository as `nrwl.angular-console` v18.95.0, appearing entirely legitimate at install time. Post-install, a multi-stage credential stealer harvests GitHub/npm tokens, AWS keys, HashiCorp Vault tokens, kubeconfig files, and 1Password vault items, then exfiltrates over three independent channels simultaneously (HTTPS, GitHub API write, DNS tunneling) specifically to defeat single-channel block lists. The NOVEL element StepSecurity's disclosure highlights: attackers used STOLEN npm OIDC tokens to request Fulcio certificate issuance and produce valid SLSA provenance attestations — breaking the industry-wide assumption that a signed release implies a trusted one, the same assumption Vector 1's forged provenance also defeats.

**Vector 4 — ClawHavoc: malicious Claude Code Skills, completing the cluster (Docker, 2026-05).** 335+ malicious skills observed across the public Claude Code skills ecosystem. An attacker publishes a malicious `.claude/skills/<name>/SKILL.md` with a high-coverage description that surfaces aggressively for many common prompts; once a victim developer installs it, Claude Code surfaces the skill on a routine prompt, and — because the skill declared broad tool access (Read + Write + Bash + Edit) — its payload runs during ordinary workflow. The payload sweeps credential locations and bulk-exfiltrates, with some variants hiding their presence via T1564 (renaming/backdating files). This is the newest vector shape in the cluster: previous three all abuse a PACKAGE/EXTENSION install surface; this one abuses the AI coding assistant's own SKILL-surfacing mechanism.

**Vector 5 — Megalodon: bulk throwaway-account GitHub Actions workflow poisoning (uncited internal source).** Attributed to the TeamPCP/UNC6780 cluster (the same actor this corpus's separately-covered `observed_teampcp_unc6780_t1195.yml` rule documents, via Google GTIG + Hudson Rock sources — this rule cross-references that overlap in its own description). The described attack chain: the actor bulk-registers 50+ GitHub accounts using disposable-email providers (10minutemail/mailinator/guerrillamail/temp-mail-style addresses) within a 6-hour window, each account opens 1-5 PRs or pushes commits to victim open-source repositories modifying `.github/workflows/*.yml` to inject a base64-encoded step payload (`run: echo <base64-blob> | base64 -d | bash`), which GitHub Actions executes on PR/push trigger, sweeping `GITHUB_TOKEN`/secrets/env vars and exfiltrating via HTTPS POST or DNS-tunneling fallback.

**Honesty note on Vector 5's sourcing and scope, worth flagging explicitly**: unlike every other rule in this note (and the overwhelming majority of this corpus), this rule's `author` field is simply `WRG-11` (not the usual "WinstonRedGuard -- sigma plugin observed rules (derived from ...)" attribution pattern), its `references` are all bare MITRE ATT&CK technique links with NO vendor/researcher/news citation for the Megalodon profile itself, and its description cites the attribution source as `internal` — i.e., this campaign's existence and TTP profile are NOT independently verifiable from this rule's own citations the way Vectors 1-4 and the rest of this corpus's `observed_*` rules are. Additionally, the rule's own description narrates a THREE-PART composite signal (base64 workflow payload + 6-hour burst window + 50+ throwaway-email account creations), but the actual `detection:` block only encodes ONE part of that (the base64 payload pattern in a `workflow_run` event) — the burst-window and account-creation-volume conditions described in prose are NOT present in the YAML `detection:` logic at all, meaning a deployment of this rule as written detects "a GitHub Actions workflow contains a base64-decode-and-execute pattern," full stop, regardless of whether any bulk-account-registration burst accompanied it. Treat this rule as the least-verified entry in this note's six, and treat any resulting hit as "a suspicious workflow payload pattern," not confirmed Megalodon/TeamPCP/UNC6780 activity, until the burst-correlation half is either built out or corroborated by an independently-citable source.

### The shared lesson (Part A)

All four vectors abuse a form of DEVELOPER-TRUSTED INSTALL SURFACE — npm package, CLI installer, VS Code extension, AI-assistant skill — and two of the four (Vectors 1 and 3) specifically defeat SUPPLY-CHAIN PROVENANCE mechanisms (SLSA/Sigstore) that exist precisely to prevent this class of attack. If your organization's defense-in-depth relies on "the release has a valid provenance attestation," Vectors 1 and 3 are concrete, disclosed counterexamples — the compromise happened upstream of, or by abusing, the attestation mechanism itself, not by forging a signature the mechanism would have caught.

### The detection signals (Part A)

- **Vector 1** (dns/network logsource): a DNS query for the `m-kosche.com` apex/subdomain family or the exact `t.m-kosche.com` IOC, OR a network connection to `185.95.159.32`, OR (an npm-family process parent combined with either DNS selection). This rule's condition uses Sigma's `1 of selection_dns_*` wildcard-count syntax — `sample_match_gate.py` initially could not evaluate this (raised `EvaluatorError` rather than a silent pass); the evaluator was extended the same day to expand `N of <prefix>*` syntax before evaluation, and the rule's sample is now mechanically verified (PASS), not merely best-effort.
- **Vector 3**: any ONE of three independent selections — a VS Code/Cursor-attributed extension-install command line naming `nrwl.angular-console`; a VS Code-attributed child process (`powershell`/`curl`/`wget`/`node`) reaching `api.github.com`, an OAuth token endpoint, or one of six credential-file paths; or a command line referencing Sigstore's `fulcio.sigstore.dev`/`rekor.sigstore.dev` endpoints or `cosign sign-blob`.
- **Vector 4**: a Claude-Code/Cursor-attributed process touching `.claude/skills/`/`SKILL.md` in its command line, COMBINED WITH (in the same event) either a credential-file reference, a bulk-POST-egress pattern, or a file-hiding indicator (`touch -t`, `Set-ItemProperty -Name LastWriteTime`, renaming `SKILL.md`).
- **Vector 5** (github/audit logsource): a `workflow_run` event whose `workflow_ref` matches a regex for the base64-decode-and-execute shell idiom (`(echo|printf)\s+[A-Za-z0-9+/]{50,}\s*\|\s*base64\s+-d\s*\|\s*(bash|sh|pwsh|powershell)`) — as noted above, this is the ENTIRE detection surface; the burst/account-volume half of the described composite signal is not encoded.

### A real rule defect found: Vector 4 (ClawHavoc)

`selection_claude_skill_install_egress` and `selection_post_install_bulk_egress`/`selection_post_install_credential_scan` all look at the SAME event's SAME `CommandLine` field, but the rule's own description narrates this as TWO SEPARATE STEPS — "(2) Victim developer installs the skill... (4) Payload sweeps credential locations... bulk-exfils." This is the third instance of a defect pattern already found twice elsewhere in this corpus today (`miasma_binding_gyp_command_substitution`, `s1ngularity_nx_npm_token_exfil`): a multi-step attack chain encoded as a single-event `and`, which a real two-step process-creation log NEVER satisfies.

Isolated test (`rule_fires`, this corpus's own evaluator):
```
Stage1 alone (skill install, separate event)         fires? False
Stage2 alone (bulk-egress POST, separate event)       fires? False
Combined (artificial, same CommandLine has both)      fires? True
```
Note also that `selection_claude_skill_install_egress`'s `ParentImage` set (`claude.exe`/`claude-code.exe`/`cursor.exe`) and `selection_post_install_credential_scan`'s `ParentImage` set (`node.exe`/`powershell.exe`/`pwsh.exe`) DO NOT OVERLAP AT ALL — a single event's `ParentImage` cannot satisfy both, so the `credential_scan` branch of the OR can never combine with the install-egress selection; only the `bulk_egress` branch (whose `ParentImage` set includes `claude.exe`/`claude-code.exe`, overlapping the install selection) can theoretically co-fire, and only via the same unrealistic single-event-contains-both-substrings path. Recommend: rewrite as a `correlation`/temporal multi-event rule, same recommendation as the other two instances of this pattern.

## Part B: The Generic "Shai-Hulud" Pair — a Documented Content Gap, Not a Fourth Cluster Vector

`observed_shai_hulud_npm_worm_t1059.yml` and `observed_shai_hulud_npm_worm_t1195.yml` are worth reading honestly rather than folded into Part A's narrative, despite sharing a "worm" theme. Their `references:` lists ARE rich and specific — StepSecurity's binding.gyp writeup, Datadog Security Labs' "Shai-Hulud 2.0" article, Unit42's npm supply-chain-attack piece, Snyk's corroboration, and a cybersecuritynews.com summary, five real, independent, technical sources describing a real npm worm campaign. But their `description:` fields are generation-Phase-6 boilerplate — literally "Breach intel signature for actor shai_hulud_npm_worm, MITRE technique T1059/T1195. Derived from 1 observed incident(s) in the WRG breach catalog," with no campaign-specific narrative at all (compare this corpus's other `observed_*` rules, which all describe the specific mechanism, IOC, and timeline the references document). Their `detection:` logic matches this same generic pattern: `t1059` fires on ANY shell process (`cmd`/`powershell`/`wscript`/`cscript`) whose command line contains `Invoke-`/`DownloadString`/`FromBase64String` — a textbook PowerShell-download-cradle heuristic that would fire on thousands of unrelated malware families and red-team tools, not anything specific to this worm. `t1195` fires on ANY unsigned executable/MSI/DLL launched from `Temp`/`Downloads`/`Installers` — again a generic unsigned-install heuristic, not this campaign's IOCs.

**This is an honest gap, not a fabricated connection**: the five references describe a real, technically detailed npm worm (self-propagating via compromised maintainer credentials, campaign-specific package names and payload behavior per Datadog's "2.0" framing implying a first wave too) — but NEITHER rule's detection logic actually encodes any of that campaign's specific IOCs, package names, or payload signatures. Deploying these two rules gives you a generic "suspicious PowerShell download cradle" and "unsigned install from a staging directory" detector — genuinely useful baseline coverage, but NOT specific evidence of the Shai-Hulud worm the references point to. Anyone relying on a hit from either rule as "this is Shai-Hulud" is over-reading what the rule actually checks.

### The detection signals (Part B)

- **t1059**: `cmd.exe`/`powershell.exe`/`wscript.exe`/`cscript.exe` with a command line containing `Invoke-`, `DownloadString`, or `FromBase64String` — a generic PowerShell-download-cradle signature.
- **t1195**: an unsigned (`Signed` field not `'true'`) `.exe`/`.msi`/`.dll` launched from a path containing `\AppData\Local\Temp\`, `\Downloads\`, or `\Installers\` — a generic unsigned-staged-install signature.

### Known limitations (Part B)

Both rules will generate substantial false-positive volume in any environment with legitimate PowerShell automation or software that self-updates from a Downloads/Temp staging path — neither rule has ANY campaign-specific narrowing condition to reduce this, unlike virtually every other `observed_*` rule in this corpus. Both are `status: test` (not `experimental`), suggesting the authoring pipeline itself flagged these as needing further work before promotion — this note's finding corroborates that flag rather than contradicting it. If this corpus's maintainers want these two rules to actually detect the Shai-Hulud campaign the references describe, they need re-authoring with the campaign's actual IOCs (package names, C2 infrastructure, specific payload behavior) from the cited Datadog/Unit42/StepSecurity/Snyk sources — the sources are already collected, they're simply not yet reflected in the `detection:` block.

## What to do right now

1. **Vector 1 (Mini Shai-Hulud)**: if you already deployed the sister NextDNS block for `m-kosche.com`, this Sigma rule gives you retrospective-hunt and SIEM-correlation value on top of that block — deploy both, not either/or.
2. **Vector 3 (nx-console)**: audit for `nrwl.angular-console` installs pinned to v18.95.0 specifically; the Sigstore-bypass detection signal is worth generalizing — any environment verifying release provenance via Sigstore should confirm its OWN OIDC token issuance path can't be abused the same way.
3. **Vector 4 (ClawHavoc)**: review the provenance/publisher reputation of any `.claude/skills/` entries already installed in your environment; per the rule's own known limitations, this is currently the weakest-VERIFIED detection of the four Part-A vectors with a same-event structural defect (see the defect above) — treat a non-hit as inconclusive, not clean.
4. **Vector 5 (Megalodon)**: treat any hit as "a base64-decode-and-execute pattern was found in a workflow run," not confirmed Megalodon/TeamPCP/UNC6780 activity — the rule's uncited sourcing and its detection-vs-description gap (see honesty note above) mean this is this note's least-verified entry; if your environment already runs `observed_teampcp_unc6780_t1195.yml` (this corpus's independently-sourced TeamPCP/UNC6780 rule), correlate hits between the two before treating either as high-confidence on its own.
5. **Part B pair**: deploy only with the explicit understanding that a hit means "generic download-cradle/unsigned-install behavior observed," not "Shai-Hulud worm confirmed" — pair with the campaign-specific IOCs from the cited sources if you want actual Shai-Hulud-specific coverage, since this rule pair does not yet provide it.
6. Deploy all six rules against the log sources each requires (dns/network for Vector 1; process_creation for Vectors 2-4 and Part B; github/audit for Vector 5).
