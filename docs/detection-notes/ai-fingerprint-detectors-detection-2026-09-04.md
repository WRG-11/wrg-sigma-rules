# Detecting AI-Generated Code: WRG's Eight ai_fingerprint Signature Detectors

Unlike every other note in this corpus, these eight rules don't detect a vulnerability — they detect a SIGNATURE: code (or code-adjacent content, like a commit message or comment) that carries the stylistic or structural marks of having been produced by an LLM rather than a human. The use case is code-review triage: knowing a change is AI-generated doesn't mean it's wrong, but it changes what a reviewer should specifically check (hallucinated dependencies, prompt-engineering leakage, padding that inflates apparent effort).

## Why this matters as a security signal, not just a style note

The referenced background (Google Cloud's threat-intelligence writeup on AI-assisted vulnerability exploitation) frames the broader context: AI-generated code and AI-assisted attack tooling are both accelerating, and being able to tell "this was AI-produced" is now a review-triage input in its own right — not because AI-generated code is inherently worse, but because it fails in DIFFERENT ways than human-authored code (hallucinated packages instead of typos, padding instead of laziness, prompt leakage instead of debug statements left in). Several of the eight detectors below map directly onto AI-specific failure modes rather than generic code smells.

## What each detector looks for

**1. `ai_prose`** — linguistic tells in comments/docstrings/strings: em-dash density above human baseline (3.83/1k words vs. Claude's ~9/1k), AI-adjacent vocabulary ("delve," "meticulous," "tapestry"), boilerplate phrases ("it is worth noting"), rule-of-three structuring. Fires only on 2+ distinct tell kinds co-occurring, since any single linguistic tell alone is weak evidence — the rule's own confidence weighting (0.20/0.80 max) reflects that low-certainty-individually, more-useful-in-combination shape.

**2. `ai_provenance`** — literal AI-tool self-declaration text: commit-trailer-style phrases (`Co-Authored-By: Claude`) or plain self-declarations (`Generated by ChatGPT`) pasted alongside generated code. Near-zero false-positive by construction — a literal declaration string has essentially one legitimate reading, and even that (a hook that strips these trailers and happens to log the stripped text) is named explicitly as the one known exception.

**3. `ansi_color_class`** — the recurring `class Colors:` pattern with hardcoded ANSI escape sequences that LLM-generated CLIs reproduce almost verbatim; production code typically reaches for `colorama`/`rich` instead.

**4. `decoy_block`** — functionally purposeless code (unused helpers, sentinel constants, demonstration scaffolding) that LLM output tends to emit as apparent padding toward a target length. Often co-occurs with hallucinated-CVSS or prompt-artifact signals (see the excluded ninth rule's own note above).

**5. `docstring_density`** — abnormally high docstring/comment-to-code ratio for production-grade source — LLM output tends to explain every line in tutorial-grade prose where human-authored code defers to well-named identifiers.

**6. `hallucinated_import`** — an `import` statement naming a specific, independently-documented package name LLM coding assistants are known to hallucinate (the curated-seed-list example: `huggingface_cli`, when the real package is `huggingface_hub`). This is the detector with the sharpest security stakes in the set: a hallucinated import name is exactly what a slopsquatting attacker registers and ships malware under, so a hit means the code references a package with no legitimate reason to exist — high confidence without requiring co-occurrence, same reasoning as `ai_provenance`.

**7. `prompt_artifacts`** — hardcoded prompt-engineering literals in source (persona prompts, anti-hallucination annotations, system-instruction fragments like "Core Judgment Rules:") — these are the residue of an LLM-augmented development process leaking into shipped code.

**8. `unicode_watermark`** — zero-width characters (U+200B/200C/200D, mid-file U+FEFF), Cyrillic/Greek homoglyphs substituted into otherwise-Latin identifiers, or curly/smart quotes appearing where a Python `SyntaxError` would result from using them as an actual string delimiter (so any occurrence sits inside string content or a comment). Mechanical, high-precision — typical of text copy-pasted directly from a chat UI, or in the homoglyph case, a possible deliberate steganographic marker.

## The detection signal (shared shape across all eight)

Each rule matches on a `detector:` field naming the specific detector plus an `evidence` string the underlying `ai_fingerprint_sigma` tool already computed — these rules are the Sigma-formatted output of a purpose-built Python analysis tool, not a generic text-pattern match against raw source. Deploying them means running that tool's actual detectors against your codebase (or CI diff), not writing a standalone grep.

## Known limitations (per detector, as the rules' own falsepositives already state)

**#1** has an estimated ~30% false-flag rate on non-native-English technical writing, and any heavily-documented repository will trip the docstring/comment-density-adjacent signals more often. **#3** is silent on pre-LLM scripts that genuinely hand-roll ANSI codes (rare but real, especially in embedded/constrained environments). **#4** can't distinguish AI-padding from legitimate dead code awaiting cleanup or deliberate feature-flag scaffolding. **#8**'s homoglyph check is scoped specifically to a confusable character embedded inside an otherwise-Latin word — it does not flag genuine non-Latin-script text on its own. **#6** has essentially no expected false positives for a listed name; the stated remediation if a hallucinated name later becomes real and registered is to remove it from the seed list rather than suppress the rule.

## What to do with a hit

Unlike the rest of this corpus, none of these eight rules indicate an attack in progress — they indicate a code-review input. A hit means: verify the flagged code was actually reviewed with the same rigor as any other change (hallucinated-import and prompt-artifact hits warrant an actual dependency/leakage check), and don't treat "detected as AI-generated" as a verdict on the code's correctness or safety by itself — it's a prompt to look more carefully at the SPECIFIC failure modes each detector maps to.
