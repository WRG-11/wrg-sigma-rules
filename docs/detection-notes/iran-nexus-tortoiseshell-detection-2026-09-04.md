# Detecting Tortoiseshell/TA456's Recruitment-Deception Chain: Fake Personas, Lookalike Domains, and Social-Platform Phishing

Eight Sigma rules covering eight stages/signals of a single social-engineering-led espionage campaign run by Tortoiseshell (also tracked as Imperial Kitten, TA456, MITRE group G0107), an Iran-nexus threat actor. Unlike this corpus's vulnerability-driven rules, this cluster detects TRADECRAFT — the actor's own operational pattern of building fake personas and lookalike infrastructure to manipulate a target into running something, rather than exploiting a software flaw. Both Meta's official 2021 takedown disclosure and Proofpoint's independent TA456 report describe the same core pattern: a long-running, patient social-engineering operation against defense-adjacent targets, using fabricated identities across multiple social platforms simultaneously.

Three of the eight (T1656.002, T1585, T1585.001) are a structurally different rule shape worth calling out up front: each ships as a Sigma **correlation** pair — a `status: test` base rule doing a single-event match, referenced by a second `type: event_count` correlation document that only alerts once the base rule's pattern repeats past a threshold within a time window. This is notable because it is the CORRECT way to express "this single event is unremarkable on its own, but N of them in a short window is the actual signal" — exactly the shape this corpus's `sample_match_gate.py` tool cannot mechanically verify (a correlation rule has no single-event `condition:` string for the evaluator to check), and exactly the shape three OTHER rules found and flagged as defects earlier in this same detection-note effort (`observed_miasma_binding_gyp_command_substitution_t1195_002`, `observed_s1ngularity_nx_npm_token_exfil_t1195_002`, `observed_clawhavoc_claude_skills_t1195_002` — see `rule-defects-found-by-sample-match-gate-2026-09-04.md`) SHOULD have used but instead expressed as a same-event `and` that can never fire on the actual multi-step attack chain they describe. These three Tortoiseshell rules are the corpus's own working reference implementation of the fix those three defective rules need.

## What each stage of the chain actually does

**1. Resource development — registering the infrastructure before the outreach begins (T1583, T1583.001).** Before any contact with a target, the actor registers freshly-created domains, often crafted to superficially resemble legitimate news, telecom, or government-adjacent brands (the rule's own selection lists patterns combining terms like `vodafone`/`bbc`/`cnn`/`reuters`/`nato`/`gov` with `news`/`media`/`press`/country-code fragments) — infrastructure staged in advance of the recruitment-deception outreach, not spun up reactively.

**2. Defense evasion — synthetic personas built with off-the-shelf generation tooling (T1656).** The actor's personas are not simply stolen photos; both source disclosures describe AI/procedurally-generated persona material as part of the operation's tradecraft. This rule flags the persona-BUILDING tooling itself — process-creation evidence of persona-generation utilities (`thispersondoesnotexist`, `faker`, `stylegan`, `generated-photos`, or a custom `persona_factory` script) invoked via scripting-capable interpreters — distinct from every other rule in this cluster, which detect the persona being USED, not built.

**3. Initial access — the phishing email carrying the recruitment-deception lure (T1566.002).** A spearphishing-via-link email using subject lines built around urgency/account-verification pretexts (`verify your account`, `password expir[ed]`, `security alert`, `account suspended`) paired with a URL path shape (`/verify/`, `/reset/`, `/secure/`, `/confirm/`) matching credential-harvesting infrastructure — explicitly excluding legitimate transactional senders (DocuSign, Adobe Sign, Mailchimp, SendGrid, Google's own notification senders) so routine business email doesn't trip this selection.

**4. Execution — the target actually clicking through from a social-platform message (T1204.001).** This is the User Execution half of the chain: a proxy-observed click whose HTTP referer traces back to a messaging surface (Outlook, Gmail, LinkedIn messaging/profile, Twitter DMs, Facebook Messenger, WhatsApp Web, Signal) landing on a destination host whose name itself carries a credential-harvesting-shaped keyword (`verify`, `secure`, `update`, `reset`, `signin`, `login`, `recovery`, `unlock`, `account`, `portal`) — again explicitly excluding known corporate-collaboration domains (SharePoint, Slack, Teams, Zoom, Atlassian, DocuSign, Adobe Sign) so ordinary work-messaging clicks don't fire this.

**5. Defense evasion — the fake persona editing its own cover profile at scale (T1656.002).** A base-rule match is a single profile-edit request against a major social platform (LinkedIn, X/Twitter, Facebook, GitHub, Medium) whose query string sets a display-name/bio/job-title field to an executive- or press-credibility-signaling value (`CEO`, `CFO`, `CTO`, `director`, `VP`, `founder`, `spokesperson`, `journalist`, `reporter`, `professor`, `researcher`, `analyst`) — one such edit is nothing (any real person legitimately updates their own title once). The correlation rule only fires when the SAME host sees six or more such edits within 30 minutes, which is the actual signal: an operator iterating through a persona's credibility-signaling fields repeatedly while building it out, not a single legitimate profile update.

**6. Resource development — bursts of fabricated accounts on the operator's own infrastructure (T1585).** A base-rule match is a single Windows Security-log account-lifecycle event (`EventID 4720` create, `4722` enable, `4738` change) — routine IT activity on its own. The correlation rule fires only when the SAME `SubjectUserName` performs six or more of these within an hour, catching an operator provisioning a batch of sockpuppet accounts from one admin identity in a short window, not ordinary day-to-day account administration.

**7. Resource development — bursts of new social-media persona signups (T1585.001).** A base-rule match is a single signup/registration request against a major platform (X/Twitter, Facebook, Instagram, LinkedIn, TikTok) — again unremarkable alone. The correlation rule fires when the SAME host produces six or more signup attempts within 30 minutes, catching an operator batch-provisioning the persona accounts that stages #5 (T1656.002) will later go on to edit and maintain.

## The shared campaign pattern

Read together, these eight rules trace one coherent operational sequence: batch-register lookalike domains and fake social accounts (T1583/T1583.001, T1585.001) → build out each persona's credibility-signaling profile fields at scale (T1656.002) → construct the actual synthetic persona material (T1656) → provision the sockpuppet accounts that run the operation (T1585) → approach a target through a personal/professional messaging platform, not corporate email (T1204.001 via T1566.002's phishing lure). The distinctive signature both sources independently emphasize is the MULTI-PLATFORM persona consistency — the same fabricated identity operating across LinkedIn, other social platforms, and direct messaging simultaneously to build the target's trust before the technical payload ever appears. The three correlation-based rules (T1656.002, T1585, T1585.001) capture the earliest, most detectable phase of this sequence: BUILDING the persona infrastructure at a volume no single legitimate user would ever produce, well before any target is even approached.

## The detection signals

- **T1583 (dns_query logsource):** a DNS query (`EventID: 22`) for a hostname matching a newly-registered-domain naming hint (`newly-registered`, `just-registered`, `reg-YYYY-MM`, `typo-domain`).
- **T1583.001 (proxy logsource):** a proxy request carrying an explicit new-domain hint in its query string AND a hostname matching the brand/news-outlet lookalike regex — both conditions required, explicitly excluding a short allowlist of the real outlets being impersonated.
- **T1656 (process_creation logsource):** a scripting-capable interpreter (`powershell.exe`, `python.exe`, `node.exe`, `cscript.exe`, `wscript.exe`, etc.) invoked with a command line referencing persona-generation tooling by name.
- **T1566.002 (email logsource):** an urgency/account-themed subject line combined with a credential-harvesting-shaped URL path, excluding a known-safe transactional-sender allowlist.
- **T1204.001 (proxy logsource):** a referer from a personal/social messaging surface landing on a host whose name carries a verification/security-themed keyword, excluding known corporate-collaboration domains.
- **T1656.002 (proxy logsource, correlation):** base = a profile-edit request to a major platform with an executive/press-credibility field value, excluding a corporate brand-management tooling allowlist (`BrandProtection`, `ExecutiveBranding`, `RecruiterAPI`, `HRTooling` user-agents); correlation = ≥6 base matches from the same host within 30 minutes.
- **T1585 (security logsource, correlation):** base = a single `EventID 4720`/`4722`/`4738` account-lifecycle event; correlation = ≥6 base matches from the same `SubjectUserName` within 1 hour.
- **T1585.001 (proxy logsource, correlation):** base = a signup/registration request to a major social platform, excluding a security-scanner/brand-protection/social-media-management tooling allowlist; correlation = ≥6 base matches from the same host within 30 minutes.

## Known limitations (per rule)

**T1583** keys entirely on the literal domain-naming convention (`newly-registered`, `reg-YYYY-MM`, etc.) appearing IN the domain name itself — real actor-registered domains rarely announce their own newness this literally in production; treat this rule's phrasing as an illustrative placeholder for whatever domain-age/reputation feed your own environment actually has (WHOIS age, a threat-intel domain-reputation API), not a literal string to expect in real traffic.

**T1583.001**'s brand-lookalike regex is necessarily incomplete — it covers the specific outlet/keyword combinations documented, not every possible lookalike a well-resourced actor could register; a domain impersonating a brand outside this list will not be caught.

**T1656** cannot distinguish an actual persona-fabrication operation from a legitimate use of the same tooling — a QA engineer testing face-generation libraries, or a developer building a `faker`-based test-data generator, will trip this rule identically. This selection is a weak, high-noise signal on its own and should be correlated with the other four rules in this cluster before escalating.

**T1566.002 and T1204.001** both rely on their respective allowlists (known transactional senders / known corporate-collaboration domains) to suppress routine business traffic — an environment using a collaboration or e-signature platform not on either list will see elevated noise from both rules until the allowlist is extended locally.

**T1656.002, T1585, and T1585.001** (the correlation trio) share one structural limitation: none of the three can distinguish a genuinely malicious volume burst from a legitimate BULK operation by the same identity — a corporate social-media team batch-editing multiple managed brand profiles, an HR/IT team provisioning many accounts during onboarding, or a marketing team launching several campaign accounts at once could all cross a ≥6-in-window threshold. Each ships with a corresponding tooling-allowlist (T1656.002/T1585.001 check `cs-user-agent` for known brand/HR/security tooling; T1585 has none, since Windows Security-log account-lifecycle events carry no user-agent field to filter on — an environment with legitimate high-volume account provisioning will need a different suppression mechanism for T1585 specifically, such as excluding known service/automation `SubjectUserName` values). The 6-in-30-minutes / 6-in-1-hour thresholds are also untuned defaults from the rule authors, not empirically derived from this specific campaign's actual operational tempo — treat them as a starting point for local calibration, not a validated cutoff.

All eight rules are dated 2021-07-08 (the disclosure date). The five non-correlation rules carry `status: experimental`; the three correlation rules' BASE documents carry `status: test` (with the correlation document itself unstatused, per Sigma's correlation-rule convention) — but across all eight, the detection logic describes a GENERALIZED tradecraft pattern (persona-driven social-platform recruitment deception), not a version-bound software vulnerability, so there is no "patched version" negative case any of these eight rules can rely on the way most of this corpus's CVE-sourced rules do; a hit here always warrants human review, not a version check.

**Verification tooling note:** this corpus's `sample_match_gate.py` (single-event Sigma evaluator, written earlier in this same detection-note effort) cannot mechanically verify the three correlation rules — its `rule_fires()` explicitly raises `EvaluatorError("no single string 'condition'")` on any rule without one, by design (it does not silently treat an unsupported shape as a pass or a fail). Their base-rule single-event logic was verified by manual read against each rule's own YAML rather than the automated gate; no `.sample.json` sidecar was written for these three, since a JSON sidecar convention built for single-event matching cannot express "N of these across a time window" either. A real regression-test story for this corpus's correlation rules is a separate, not-yet-built piece of tooling.

## What to do right now

1. If your organization has employees in defense, aerospace, or government-adjacent roles, treat unsolicited LinkedIn/social-platform outreach involving an unusually rapid rapport-building pattern followed by a request to click a link or run a file as consistent with this actor's documented tradecraft, independent of whether any of these eight rules fire.
2. Correlate hits across this cluster rather than acting on any single rule alone — the persona-generation signal (T1656) especially is weak in isolation and gains confidence when it co-occurs with the infrastructure (T1583/T1583.001), the volume-burst signals (T1656.002/T1585/T1585.001), or the delivery (T1566.002/T1204.001) signals.
3. Extend the relevant allowlists (transactional senders, corporate-collaboration domains, brand/HR/security tooling user-agents) to match your own organization's actual tool stack before deploying T1566.002/T1204.001/T1656.002/T1585.001, or expect elevated false-positive volume — and for T1585 specifically, build a `SubjectUserName`-based exclusion for known automation identities since no user-agent field exists to filter on there.
4. If you write or maintain other Sigma rules describing a multi-step attack chain where individual steps are unremarkable but repetition in a short window is the actual signal, use these three rules' base+correlation structure as your reference — NOT a same-event `and` across selections keyed to different steps, which is the exact defect pattern this detection-note effort found three times elsewhere in this corpus.
5. Deploy all eight detection rules against the log sources each requires (dns_query, proxy ×4, email, process_creation, security).
