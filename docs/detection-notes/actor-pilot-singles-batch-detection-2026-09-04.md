# Five Distinct High-Signal Disclosures: TanStack's Pwn Request Postmortem, Ollama's Unsigned Updater, Storm-2949's Cloud Credential Harvest, Copilot's fetchPage Bypass, N-central's In-the-Wild RMM Bypass

Five unrelated, high-quality disclosures — a vendor's own official postmortem, two chained CERT-coordinated CVEs, a named Microsoft threat-intelligence campaign, a cross-verified tool-scope bypass, and a CISA-KEV-listed actively-exploited RMM auth bypass — each distinct enough to stand alone rather than share a theme.

## What each disclosure actually documents

**1. TanStack's own postmortem: a textbook "Pwn Request" chained into OIDC token theft (2026-05-11, 19:20-19:26 UTC).** An attacker published 84 malicious versions across 42 `@tanstack/*` npm packages in under six minutes (later expanded, per Orca's tracking, to 373 malicious versions across 169 npm packages and 2 PyPI packages). Attack chain, confirmed identically by TanStack's own postmortem AND independently by Orca Security: (1) attacker opens a pull request from a fork against a workflow configured with the `pull_request_target` trigger — the well-known "Pwn Request" GitHub Actions misconfiguration class, which runs with the BASE repository's elevated permissions/secrets even though triggered by untrusted fork content; (2) attacker poisons the GitHub Actions cache with a malicious pnpm store; (3) a legitimate maintainer's later merge triggers the release workflow, restores the poisoned cache, and attacker-controlled code extracts the workflow's OIDC token directly from the runner process's own memory (`/proc/<pid>/mem`); (4) the stolen OIDC token — never a stolen long-lived credential — publishes malicious versions with VALID npm provenance attestations, meaning provenance verification alone would not have caught this. This rule targets the initiating, detectable event every source agrees the chain requires: a `pull_request_target`-triggered workflow run whose PR originates from a fork.

**2. Ollama for Windows: two independently-real bugs chain into unattended persistent code execution (CVE-2026-42248 + CVE-2026-42249, cert.pl, affecting 0.12.10-0.17.5).** First bug: unlike other platforms, Ollama for Windows' update-verification routine unconditionally returns success — no signature or trust validation runs before an update payload is staged or executed. Second bug: the client builds the local staging file path using values taken directly from HTTP response headers, passed to `filepath.Join` with no validation, so a header containing `../` traversal sequences resolves outside the intended staging directory. Chained: an attacker positioned on the network path (or controlling/spoofing the update endpoint) writes an arbitrary executable to any location the current user can reach, including the Windows Startup folder — and because Ollama for Windows performs SILENT automatic updates with no user interaction, the two bugs together deliver a malicious executable straight into Startup, running on next login with no signature check and no prompt. No patched version was confirmed by maintainers as of the write-up.

**3. Storm-2949: SSPR-abuse account takeover into Azure management-plane credential harvesting (2026-05-18, Microsoft Threat Intelligence).** Confirmed by both Microsoft's own advisory and at least one independent write-up: initial access via abuse of Microsoft Entra ID's Self-Service Password Reset flow — the actor initiates an SSPR request against a target account and social-engineers the victim (posing as internal IT support) into approving the resulting MFA prompt, letting the actor reset the password AND strip existing authentication methods, eliminating MFA as a control entirely. The actor then uses Microsoft Graph API plus custom Python (Azure SDK) scripts to enumerate users/roles/service principals/applications, searches OneDrive/SharePoint for IT-ops files and VPN configs, and installs a renamed ScreenConnect for persistent access. This rule targets the credential-harvesting stage specifically, using exact Azure Resource Manager operation names published directly in Microsoft's advisory: publishing-profile retrieval (`publishxml/action`, returns FTP/WebDeploy cleartext credentials), SQL firewall-rule creation (opens external DB access), and storage-account key listing (`listkeys/action`, harvests long-lived access keys).

**4. GitHub Copilot's `fetchPage` tool: a shared web-fetch tool that skips the workspace-boundary check its sibling tool enforces (CVE-2025-66389, blindcyber.com).** VS Code's `fetchPage` tool is designed for fetching web pages and is shared between HTTP(S) and `file://` schemes; Copilot invokes it as a thin wrapper WITHOUT re-applying the explicit workspace/open-tab containment check its own `readFile` tool enforces (per `fetchPageTool.ts:152`, cited by the source at the exact line). This lets an INDIRECT prompt injection — content the agent reads from elsewhere, not a direct user instruction — steer Copilot into fetching a local path outside the workspace (the write-up's example: `file:///etc/passwd`), without the user-approval gate this would otherwise require for untrusted web URLs. Documented exfiltration path chains this with a second VS Code behavior: content written into a JSON file's `$schema` field triggers an automatic IntelliSense fetch of that URL, so an attacker-controlled schema endpoint receives file content appended as a side effect of normal editor behavior. Corroborated by Microsoft's own confirmation and fix.

**5. N-central: an actively-exploited-in-the-wild RMM auth-bypass, added to CISA KEV within 48 hours of vendor disclosure (CVE-2026-18577, an incomplete fix for CVE-2026-18556).** Added to CISA's Known Exploited Vulnerabilities catalog 2026-08-03 after N-able's own advisory disclosed in-the-wild exploitation since 2026-08-01. Cross-verified against two independent incident-response/threat-intel vendors (Huntress and Rapid7), which report MATCHING post-exploitation artifacts — not just the same narrative, the same specific indicators. Post-auth-bypass, attackers abuse N-central's Take Control functionality (via the legitimate "MSP Support" account) to reach managed downstream endpoints, then establish persistence via a Cloudflare Tunnel registered as a Windows service named "Cloudflared," alongside a suspicious `svchost.exe` binary planted in the compromised user's Documents folder — masquerading as the legitimate Windows `svchost.exe`, which never legitimately runs from a user profile path. Verification discipline: both artifacts (Documents-folder `svchost.exe`, Cloudflared service name) appear identically in both Huntress's and Rapid7's independent write-ups; the network IOCs both sources also list (a handful of static IPs) are deliberately excluded from this rule's detection logic, since both sources themselves note most of those IPs resolve to shared Mullvad/NordVPN exit-node infrastructure, not attacker-exclusive hosting.

## The detection signals

- **#1 (github/audit logsource):** a `workflow_run` event whose `workflow_ref` contains `pull_request_target` AND whose triggering pull request's `head.repo.fork` is `true`.
- **#2 (file_event logsource):** a new executable created inside a user's Startup folder (`...\Microsoft\Windows\Start Menu\Programs\Startup\`), attributed to a process image containing `ollama`.
- **#3 (azure activitylogs logsource):** any single occurrence of the three named ARM operations (publish-profile retrieval, SQL firewall-rule write, storage-account key listing) — deliberately `level: high` not `critical` since each is individually a real admin action; true correlation (same caller, multiple operations, short window) needs a Sigma correlation document this corpus's rule format doesn't yet render.
- **#4 (file_access logsource):** a `Code.exe`/`code.exe`-attributed process whose target filename contains `file://` AND references a sensitive out-of-workspace path (`/etc/passwd`, `/etc/shadow`, `.ssh/id_`, `.aws/credentials`).
- **#5 (process_creation logsource):** an `svchost.exe`-named image running from a `\Documents\` path (masquerade) OR a command line containing `cloudflared`/`Cloudflared` (tunnel persistence) — either condition alone is sufficient.

## Known limitations (per rule)

**#1** should not fire on a deliberately-hardened `pull_request_target` workflow that already restricts itself to read-only permissions and never checks out/executes fork content (the safe pattern) — confirm the workflow's actual permission/checkout behavior before escalating. Bot-authored dependency-update PRs from forks on repos using `pull_request_target` for label/triage automation only are also expected noise.

**#2** has no fixed-version negative case — treat every match as needing manual review. Cannot fully rule out a user/admin legitimately using Ollama's own updater to place a shortcut in Startup by explicit configuration, though ordinary updates replace the existing binary rather than adding a new Startup entry; a log source that can't distinguish "new Startup file" from "existing file rewritten" may alias the two.

**#3** cannot itself distinguish a legitimate DevOps/CI pipeline identity performing routine publish-profile/key-rotation operations, or IaC tooling (Terraform/Bicep/ARM) running from a shared automation identity, from the actual credential-harvest stage — reviewers should cross-check `CallerIpAddress`/`Caller` across hits before escalating, since single-operation matches on legitimate automation are expected. The exact Defender-disabling PowerShell cmdlets and renamed ScreenConnect service name are described narratively by the sources but no verbatim string was published by either — deliberately left out of this rule's detection logic rather than guessed.

**#4** has no specific patched version documented in available sources, unlike most rules in this corpus that name an exact cutoff — re-evaluate once an authoritative advisory with a version range is published. This rule also only detects the read/access half of the chain, not the JSON-schema exfiltration half, since no log-observable signature for the schema-fetch step is documented in the source material.

**#5** cannot fully rule out legitimate, sanctioned use of Cloudflare Tunnel for remote access elsewhere in the environment — verify against a known-tunnel inventory before escalating on the Cloudflared selection alone. A user manually saving/extracting an unrelated file literally named `svchost.exe` into Documents is rare but not impossible; the real distinguishing signal is EXECUTION, not presence, which this rule (process_creation logsource) already captures correctly.

## What to do right now

1. **#1**: audit every workflow using `pull_request_target` for whether it checks out or executes fork content — if it does, this is the exact misconfiguration class TanStack's postmortem documents; consider rotating to `pull_request` + a separate, permission-scoped follow-up job instead.
2. **#2**: no patch confirmed — restrict Ollama for Windows' network path to the legitimate update endpoint, or disable silent auto-update until a fix ships.
3. **#3**: if you haven't already, review your Entra ID SSPR flow for social-engineering resilience (does approving an MFA prompt actually require the requester to be who they claim) — this is the actual root cause, not the three ARM operations this rule detects downstream of it.
4. **#4**: no patch confirmed in available sources — be aware any AI coding assistant sharing a single "fetch" tool across web and local-file schemes may carry the same scope-bypass shape; check whether your own tooling re-applies workspace containment on every code path that can reach a `file://` target, not just the ones an operator remembers to gate.
5. **#5**: patch/upgrade per N-able's advisory immediately if not already applied — this vulnerability is confirmed actively exploited, not theoretical; also audit for existing Cloudflare Tunnel services and Documents-folder executables as a compromise-assessment step independent of whether this rule has fired, since CISA KEV listing means opportunistic scanning against this CVE should be assumed ongoing.
6. Deploy all five detection rules above against the log sources each requires.
